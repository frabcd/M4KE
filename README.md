# M4KE

> **让创意进入工程流程。基于 DGX Spark 的本地 AI 设计与制造工作台。**

**团队：逆熵｜第三届 DGX Spark 黑客松｜2026.09.29**

M4KE 将**自然语言、大模型、原生 CAD 与工程工具**连接起来，为创作者提供从想法描述到设计审阅、零件选型、接线和装配准备的统一工作空间。它以小型玩具和机电创作为切入点，让复杂的工程流程能够通过对话、三维交互和工具反馈逐步展开。

**M4KE 的核心价值，是把 AI 的设计能力接到真实的工程工具上。** 模型负责理解意图和提出方案，CAD 内核负责生成几何，检查工具负责发现问题，工作台负责把设计、BOM、接线和装配信息组织成可追踪的项目。每一次修改都能回到具体零件、具体版本和具体检查依据。

- **创作入口统一**：用自然语言提出需求，在三维视口选中零件继续修改。
- **工程表达完整**：结构化设计与原生 CAD、STEP / STL、BOM、接线和装配说明相互关联。
- **反馈进入设计过程**：几何、电气与参数检查为 Agent 提供明确的修复依据。
- **本地计算可控**：DGX Spark 承载模型推理与工程工具，离线模式使用预先准备的模型和资产。
- **项目能够持续迭代**：候选版本、来源身份和检查记录贯穿设计流程。

## ✨ M4KE 的核心优势

### 1. 从需求到装配的连续工作流

M4KE 将需求、设计、修改、检查与导出组织成连续工作流，让用户围绕同一个项目推进创作：

| 阶段 | 系统支持 |
|---|---|
| **需求描述** | AI 追问关键缺口，区分用户答案与系统假设 |
| **设计生成** | 生成结构化设计、零件与候选方案 |
| **局部修改** | 根据选中的零件和修改意图生成候选版本 |
| **工程验证** | CAD、数值计算、电气检查与有界修复 |
| **导出与装配** | 模型、BOM、接线信息和逐步装配说明 |

设计候选不会未经确认直接覆盖已有版本；**数字检查通过 ≠ 实物测试通过**。

### 2. 让零件成为 AI 的上下文

用户可以在三维视口或零件大纲中选择具体零件，并查看其用途、位置理由、选型依据、材料和来源。

例如：

> “让外壳更像 F1 赛车。”

系统可以将当前选中的外壳作为修改上下文，而不是重新生成整个项目。

### 3. 三维预览与制造文件保持对应

前端使用 **Three.js** 展示模型，并记录毫米单位、源文件身份和几何哈希。

概念预览与原生 CAD 明确区分：CAD 失败时不会用一个“好看的示意模型”冒充真实工程结果。

### 4. 接线与装配说明跟随版本

电气视图区分电源、地线、信号和电机输出，并展示两端元件、引脚、建议线色和线规。

装配教程基于当前版本的真实网格生成步骤，并支持逐步查看、播放和重播。

### 5. 一台 DGX Spark，连接 AI 推理与工程计算

模型推理、项目服务和 CAD 工具可以在同一台 DGX Spark 上协同运行，浏览器提供统一操作界面。GPU 承担本地模型推理，CPU 运行项目编排、资料处理和 CAD 任务；通过阶段化上下文、受约束输出和有界修复，把计算资源用于具体设计任务。

这种部署方式让模型、资产和项目数据的使用范围由本地环境控制，也为离线创作、模型切换和工程工具扩展提供基础。

### 6. 面向扩展的 Agent + Skills 架构

需求理解、元件选型、局部修改、验证规划和修复各自拥有明确的输入、输出与边界。新的模型、元件资料和工程检查可以通过对应接口接入；设计记录保留来源与版本信息，便于继续审阅和迭代。

## 🧠 Agent + Skills

M4KE 将**“提出设计”**和**“认定结果”**分开：

- **Qwen / Agent**：理解需求、选择方案、提出修改。
- **程序与工具**：执行受约束操作、生成 CAD、进行检查。
- **验证结果**：只能由对应工具产生，模型不能自行宣布“通过”。

### Skills

| Skill | 输入 | 输出 / 边界 |
|---|---|---|
| **需求与设计** | 用户需求、回答、目录、模型资料 | 关键问题或结构化设计 |
| **模型库与选型** | 组件身份、源文件、接口资料 | 可用几何、候选资料及缺口 |
| **局部修改** | 当前版本、选中件、修改意图 | 修改候选，不直接覆盖设计 |
| **验证规划与评审** | 设计、工具检查报告 | 检查重点与风险 |
| **受约束修复** | 设计及检查错误 | 提出修改并重新交给工具验证 |

核心闭环：

```text
工具发现问题
      ↓
Qwen 分析并提出修复
      ↓
生成新候选
      ↓
工具重新检查
      ↓
通过 / 继续反馈
```

修复采用**有界重试**，保留失败记录，避免无限循环或由程序偷偷生成“正确答案”。

## 🏗️ 技术架构

```text
用户自然语言需求
        ↓
Vue 3 + Three.js 工作台
        ↓
Node.js 项目服务与流程编排
        ├── Qwen 本地推理
        │     └── 设计 / 选型 / 修改 / 验证 Skills
        ├── 元件模型库与资料检索
        ├── Python + CadQuery 原生 CAD
        ├── 工程计算与电气检查
        └── 版本化文件与检查记录
        ↓
候选确认 / 问题反馈
        ↓
模型 + BOM + 接线 + 装配说明
```

### 主要技术

| 层次 | 技术 | 用途 |
|---|---|---|
| 计算平台 | **NVIDIA DGX Spark / GB10** | 本地模型推理与工具运行 |
| 本地模型 | **Qwen3.6 35B A3B FP8** | 设计、修改与推理 |
| 推理服务 | **vLLM / Ollama** | 本地模型服务适配 |
| 前端 | **Vue 3 / TypeScript / Vite / Pinia** | 工作台与状态管理 |
| 三维 | **Three.js** | 模型预览与交互 |
| 后端 | **Node.js** | 工作流、接口、文件与版本管理 |
| CAD | **Python / CadQuery / Open CASCADE** | 原生 CAD、STEP / STL |
| 工具连接 | **MCP / 可选 SearXNG** | 元件资料与缓存检索 |
| 测试 | **Node / Python / Playwright** | 软件与浏览器回归 |

## ⚡ DGX Spark 与本地推理

M4KE 的本地优先架构将模型推理、项目服务、资料处理和 CAD 工具组织在 DGX Spark 上：

- **GPU**：本地 Qwen 推理
- **CPU**：项目服务、资料处理与 CAD 任务
- **浏览器**：工作台交互与三维显示

本地推理配置示例：

| 配置 | 设置 |
|---|---|
| 模型 | `qwen3.6-35b-fp8` |
| 服务 | vLLM |
| 最大上下文 | `65536` |
| 最大序列并发 | `1` |
| KV Cache | FP8 |
| GPU memory target | `0.55` |

### 优化思路

- FP8 KV Cache 降低内存占用
- 限制并发，减少统一内存竞争
- 根据任务类型提供不同上下文
- 局部修改优先返回变更字段，减少完整重写
- 保留失败结果和真实运行阶段
- Three.js 视口按需更新，减少不必要的 GPU 工作

## 🔧 CAD 与元件模型库

M4KE 不把“能显示”当成“能装配”。

元件资产记录：

- 组件身份
- 来源
- 单位
- 原始坐标
- 文件哈希
- 接口与安装资料

并区分：

1. 可进入原生 CAD 流程的资产
2. 仅用于视觉参考的模型
3. 仍需审核的候选资料

采购信息和公开资料可通过本地目录、缓存与 MCP 接口提供给 Agent。检索结果带有来源与缓存信息，但**网址存在不等于实时库存、价格或型号兼容性已经确认**。

目前未接入可用的嘉立创 EDA PCB 自动布局布线服务，也不生成已验证的 Gerber。

## 🧪 验证流程

工程检查围绕当前设计版本执行，覆盖原生 CAD、几何关系、电气连接、参数约束和装配信息。检查发现的问题会反馈给设计与修复流程，并保留对应版本、来源和检查记录。

软件回归使用 Node、Python 和 Playwright，分别检查服务逻辑、工具流程和浏览器交互。实物验证需结合实际采购件、打印材料和装配条件，检查尺寸配合、接线、声音响应、运动及停止行为。

## 📦 安装与运行

### 环境

目标环境：

- Linux aarch64
- Node.js ≥ 22.12
- Python 3.12
- 与 DGX Spark / GB10 匹配的 NVIDIA 驱动与推理环境

安装项目依赖并执行 smoke test：

```bash
python3 scripts/setup-submission.py --smoke
```

启动已准备好的本地 Qwen / vLLM 服务后：

```bash
export M4KE_INFERENCE_PROVIDER=vllm
export OLLAMA_URL=http://127.0.0.1:18007
export QWEN_MODEL=qwen3.6-35b-fp8
export PORT=4173

npm start
```

本机访问：

```text
http://127.0.0.1:4173/
```

完整部署、资产恢复与离线准备见 [部署说明](docs/submission/DEPLOYMENT.md)。

### DGX 本地与离线运行

- 预先准备模型、CAD 环境、依赖与获准使用的元件资产后，使用 `npm run start:offline`。离线模式关闭联网检索并拒绝在线模型桥接。
- 使用 `python3 scripts/dgx-preflight.py` 检查本机准备状态；运行步骤见 [DGX-only 运行指南](docs/dgx-only-offline.md)。
- 行驶仿真视图基于 Three.js + Rapier，允许调整质量、轮径、电机和阻力假设，观察声控响应、制动与碰撞。仿真属于估算，用于设计探索。


[文档导航](docs/README.md) · [MIT 许可证](LICENSE)

> 模型权重、第三方 CAD、元件数据库和切片器需按各自许可单独准备，不包含在源码包中。

## 🚧 扩展方向

### 1. 更完整的问题反馈

一次收集所有可独立执行的几何、电气和参数检查，将相关错误一起反馈给 Qwen，而不是只返回第一个失败。

### 2. 提高组件接口质量

继续审核模型库中的：

- 单位
- 安装基准
- 孔位
- 端子
- 接口信息

扩大真正可以可靠用于工程流程的组件范围。

### 3. 建立固定端到端 Benchmark

使用相同的需求、资产版本和通过条件，对不同模型与推理配置比较：

- 成功 / 失败
- 耗时
- 人工决策次数
- 检查失败类型

### 4. 将实物反馈纳入迭代

实际采购、打印和装配，并测量：

- 尺寸配合
- 接线
- 声音阈值
- 运动
- 停止行为

再将实物结果反馈到软件检查和装配教程中。
